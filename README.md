# 诗词联票的核销归属与跨期结算解释

联票可以换票、部分退费、分馆使用；收款周、到馆周和馆方收到调整单的周
往往不在同一期间。本项目把订单、渠道资金流水、展馆核销与有效分成协议
做成一套运营和结算都能复核的分析工具。

## 快速开始

```bash
python3 -m ticket_ledger --data data                       # 文本报告
python3 -m ticket_ledger --data data --json                # 机器可读报告
python3 -m ticket_ledger --data data --period 2026-10      # 指定运营对账期间
python3 -m ticket_ledger --data data --as-of 2026-10-31    # 只看该日前的票务事件
python3 -m ticket_ledger --data data --current-period 2026-11
python3 -m ticket_ledger --data data --strict                  # 业务告警也返回非零
```

需要 Python 3.11+，仅用标准库。存在协议冲突/缺失、订单被阻止结算时，
命令以状态码 1 退出；数据格式错误以状态码 2 退出。

## 数据文件

| 文件 | 作用 |
| --- | --- |
| `data/orders.csv` | 订单渠道、票种、币种、售价（最小单位） |
| `data/ticket_events.csv` | 售出、换票、核销/入馆、部分退款；可选 `recorded_at` 列记录"何时进入台账" |
| `data/agreements.csv` | 协议适用范围（馆×票种×渠道×日期）、分成比例 bp、单馆上限；可选 `settlement_lag_days` |
| `data/closes.csv` | 财务已确认的历史账期金额，确认后原单锁定；可选 `basis_as_of` 固定复核依据时点 |

空字段表示未提供。可选列 `ticket_events.recorded_at`、`agreements.settlement_lag_days`、
`closes.basis_as_of` 分别回答"关账时是否已经收到这条记录""协议约定的结算时点
是否已到""对方当时按什么依据复核"。

## 计算口径

**本金守恒**（每个订单、每种币种分别成立）：

```
售价 = 已退款 + Σ馆方使用份额 + 暂未归属
暂未归属 = 未签约比例 + 逐笔取整零头 + 协议封顶余额
```

* 每笔馆方份额 = `向下取整(可分配本金 × 该馆协议比例)`，独立可复核；
  零头留在"暂未归属"，有明确的细分来源，不会被随手塞给某一家馆。
* 同一订单同一馆多次核销只计一次份额（第二次起记 `repeat_of`），
  避免重复分配本金；但运营视图照常记录每次到馆。
* 各馆协议比例合计超过 100% 时，按同一比例统一压缩并告警，不偏袒任何一馆。
* 协议按 `馆 + 票种 + 渠道（含通配 *） + 核销日` 解析：渠道专属协议优先于
  通配协议；同等具体程度命中多份（重叠）或一份都没有（缺失）时，**阻止该
  订单结算**，本金留在未归属，绝不任选一个版本。
* 协议区间按 `[start, end)` 解释，后一份协议从起始日接管。

## 换票与入馆

换票只改写票据标识，不改变售价，也不新增可分配本金。换票前发生在旧票上
的入馆记录依法保留；换票后仍用旧票核销会作为票据链问题阻止订单结算。

## 结算时点与关账

* 核销只产生"馆方使用份额"（`待财务确认`）。协议 `settlement_lag_days`
  可标出结算时点是否已到，但**只有 `closes.csv` 的已确认记录才变成
  `已确认待付`**。
* 已确认金额按"原账期末已到馆、且关账确认时已收到"的当时依据摊到馆方，
  对方可按当时依据复核原单。原单永不修改。
* 关账后补来的核销或部分退款：不回写旧账期，在当前账期生成**逐馆调整单**，
  写明调整额、原单、原账期与原因。退款差额按各馆协议比例分担，不会全部
  推给补录的那家馆。
* 关闭订单在关账时完全没有馆方使用记录时，后续本金变化不自动向任何馆方
  分摊，单独列入 `使用记录未交齐（依据待补）`，等财务补依据或裁决。

## 报告结构

`--json` 输出（文本报告同序）：

1. `meta` / `warnings` / `conservation`：口径、每币种守恒校验
2. `orders`：逐单份额、暂未归属细分、分配轨迹（含每笔精确份额与封顶削减）
3. `sales`：渠道收款流水，按售出日归期、按币种/期间合计
4. `agreements`：每次核销命中的候选协议、选中版本、命中原因
5. `ticket_events`：事件链（换票前后的票据、记录时间）
6. `financial`：六个**互不合并**的桶
   - `confirmed` 已确认待付（历史关账锁定）
   - `pending` 当前账期待财务确认
   - `adjustments` 调整待确认（逐笔对应原单）
   - `unallocated` 暂未归属
   - `unallocated_movements` 未归属变动说明（与调整互为镜像，不计负债）
   - `basis_pending` 使用记录未交齐
   - `blocked` 协议冲突/缺失，阻止结算
7. `recognition_detail`：每笔历史关账当时的依据（协议、到馆日、记录日、份额）
8. `operations`：按真实到馆日期的日/周/月视图
9. `reconciliation`：逐馆解释"运营按到馆日的份额"与"财务本期金额"的差异，
   并给出 `explained_ok` 自检；订单级已确认金额单列 `order_level_confirmed`

## 验证

```bash
python3 -m unittest discover -s tests -v
```

测试覆盖：换票不重复分配本金、换票前入馆保留、退款按比例分担、取整零头
可追溯、协议封顶不外溢、比例超额压缩、渠道专属优先、重叠/缺失阻断、
关账依据按 `recorded_at` 截断、关账后补录生成调整单且不改旧单、多币种守恒、
运营与财务对账差异可解释。
